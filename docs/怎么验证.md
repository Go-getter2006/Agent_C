# 怎么验证

每一部分怎么确认它是对的。能自动检查的都写成了测试；需要真实环境的，写了具体步骤。

## 1. 自动测试

```bash
cd backend
python -m pytest tests -q
```

共 135 项，默认用内存 SQLite，两分钟左右。同一套测试可以跑在 PostgreSQL 上：

```bash
TEST_DATABASE_URL=postgresql+psycopg://用户:密码@主机:5432/一个空库 python -m pytest tests -q
```

注意这会清空那个库里的所有表。PostgreSQL 上每个用到演示数据的测试都要重新入库一次，整套要跑十几分钟。开发时在 PostgreSQL 16 上跑过，78 项全部通过。

## 2. 连真实的 XDOJ（我没有账号，这一步需要你来做）

最简单的做法：`./run.sh` 启动，在登录页选“教师”，用 XDOJ 教师账号登录，然后打开“数据源”页：

- 顶部如果有红色的“后台同步没有在运行”，说明同步没起来（正常用 `./run.sh` 启动不会出现）；
- “上次同步名单和作业”几分钟内会出现时间，“名下的班级”“已同步的提交”开始增长；
- 有问题时看启动的那个终端里的日志，搜“后台同步”“XDOJ”。

名单同步下来以后，用名单里某个学生的学号和他的 XDOJ 密码登录学生端，确认学生登录这条路是通的。

想在命令行里一步一步核对（推荐第一次这样做），在 `.env` 里填 `XDOJ_USER`、`XDOJ_PASS`（地址不用填，就是 C 语言那台），然后：

**第一步：只测登录。**

```bash
python -m app.cli init-db
python -m app.cli login-test
```

应当看到“登录成功”。失败的话请把提示发给我；程序不会打印密码。

**第二步：核对字段名。** 这一步只发 5 个请求。

```bash
python -m app.cli xdoj-probe
```

它会打印四个列表接口第一行的字段名和类型（不打印值）。请对照下面的表，哪个字段没有，告诉我实际叫什么：

| 接口 | 程序要找的字段（任意一个候选名存在即可） |
|---|---|
| `/class/list.do` | `classId` 或 `id`；`className`；`ownerId` |
| `/contest/list.do` | `id`；`title`；`startTime`；`endTime`；`classes`（布置给哪些班）；`problems`（没有的话程序会去调 `/contest/problems.do`） |
| `/problem/list.do` | `id`；`title`；`categoryName`；`tags`；`timeLimit`；`memoryLimit` |
| `/submission/list.do` | `id`；`userId`；`userName`；`problemId`；`contestId`；`classId`；`submitTime`；结果是 `judgementStr`、`judgementText`、`resultStr`、`result`、`judgement` 之一；`points` |

特别要看：作业的 `classes` 是不是真的存在。学生“只能看到老师布置给他班级的作业”全靠它。

**第三步：小规模试跑。**

```bash
python -m app.cli sync-meta --max-requests 200     # 班级、名单、作业、一部分题
python -m app.cli backfill --max-requests 300      # 最早的一批提交和它们的详情
python -m app.cli stats
python -m app.cli assemble 某个提交编号              # 和教师端提交详情页显示的对一下
```

要看的：

- `stats` 里各表的行数合不合理，最近请求的成功率是不是 100%；
- 日志里有没有“不认识的评测结果”“不认识的测试点结果”的告警。有的话把那几种结果的文字告诉我，我加到归一化的表里（`taxonomy/enums.py`）；
- `assemble` 的结果和网页上的是否一致，尤其是失败测试点的输入、期望输出、实际输出；
- 一条编译错误的提交：`compileOutput` 有内容，`testCases` 为空；
- 库里搜不到任何学生密码：`sqlite3 data/agent.sqlite3 .dump | grep -i 某个学生的密码` 应当没有结果。

**第四步：完整回填和常驻。**

```bash
python -m app.cli backfill          # 约 6800 条提交，按每秒 2 个请求大约 4 小时，可以分几晚做
python -m app.cli daemon
```

附件二第 10 节的验收标准在这一步做：行数等于接口的 `totalCount`；随机抽 20 条和网页对比；`sync_request_log` 里相邻请求间隔不小于配置值；在 XDOJ 上交一条提交，10 秒内出现在库里；停一小时再启动，积压能自动消化。

## 4. 大模型（需要 DeepSeek 的 key）

在 `.env` 里填 `DEEPSEEK_API_KEY`，重启。

- 对话：同样的操作，回复会比模板自然，但仍然受规则表约束。可以在库里看 `chat_steps`：`reply_source` 是 `llm` 还是 `template`，`check_result` 里记着没通过校验的原因，`retries` 是重写了几次。
- 标注：`python -m app.cli label-pending` 会把还没标的题目和提交标一遍。之后抽查 `problem_labels`、`submission_labels`。
- 费用：`llm_calls` 表里有每次调用的提示词编号、耗时、token 数和按 `.env` 里单价算的费用。

## 5. 沙箱

```bash
python -m app.cli quiz-verify       # 题库里每道题都应当“通过”
```

本机直接运行的方式下已经确认：死循环 1 秒后被杀；访问空指针记为运行错误；写文件被拦；连网失败；再建进程失败；申请 200MB 内存失败。compose 里的沙箱容器另外加了没有网络、只读文件系统、去掉特权，这部分要在部署的机器上确认一次：进容器执行 `ping`、`touch /x` 都应当失败。
